# Day 8 Reflection

The hardest concept in this course was transactions and isolation — specifically understanding what actually happens when two requests race. My first mental model was "the database handles it," which is true but useless in practice: it only handles it if your statements are written so the race lands inside a single guarded operation. The seat-hold design in my capstone is where it finally clicked. Writing `UPDATE seats ... WHERE state = 'available'` and checking the affected row count made it concrete: the second transaction's WHERE clause simply matches fewer rows, because the first one's row lock serialized them. I overcame the confusion by reasoning through a timeline of two overlapping requests on paper, then verifying my reasoning against real constraint behavior (a partial unique index that makes double-selling physically impossible, even if my code were wrong).

If I improved one part of the capstone based on feedback, it would be my traffic estimates. My first draft multiplied averages and called it a peak; feedback pushed me to model the shape of the spike instead — 333 buyers per second for ten minutes, with polling amplification that could turn thousands of reads into tens of thousands. Estimating the *ratio* of reads to real transactions (about 200:1) turned out to be the most useful number in the whole document, because it justifies every architectural choice that followed: queue the arrivals, cache the reads, keep the writes small and consistent.

Next I want to learn how these ideas behave at larger scale: sharding, distributed transactions, and how real systems decide when a single strongly-consistent database stops being enough. I also want hands-on practice with Redis-based queues and rate limiting, since I leaned on them heavily in this design without having built one myself.
